3. 保持できるようにしたデータ

課題の核心「リロードしても消えないデータ」は、Case Review のフォローアップ編集内容です。

データ内容いつ保存されるか
永続化フォローアップ文書 Review Comment / Vessel Revision EN / Handover Note / Training Point / Owner Summary JP / Internal Audit Checklist の編集テキスト テキストエリアを編集して保存したとき
永続化承認ステータス Supervisor 承認・DP 承認の記録、タブごとの draft / reviewing / approved 状態 承認ボタンを押したとき
参照のみ検査ケース・指摘 船舶名・港・指摘内容・リスクレベル・アラート ビルド時に同梱の JSON から読み込み（変更不可）
参照のみ過去指摘データベース 16件の匿名化 deficiency（船・港・カテゴリ・ステータス） Supabase から SELECT（読み取り専用）

デモ確認方法（リロードしても消えないことを確認）

  1. アプリを開き、P2 で指摘を1件選択
  2. P4 の Review Comment タブでテキストを編集して保存
  3. ブラウザをリロード（F5）
  4. 同じ指摘・同じタブを開く → 編集内容が残っている

保存先用途選んだ理由
localStorage ユーザーの編集・承認（課題の「記憶」） 今月のプロトタイプでは認証・サーバー API なし。 ブラウザ内に保存すればリロード後も残り、実装が最もシンプル。 zod でスキーマ検証し、壊れたデータは無視する安全策も入れた。
JSON ファイル デモ用の検査ケース・指摘マスター 静的エクスポート（Vercel）で DB 接続なしでも Case Review が動く。 匿名化サンプルデータを Git で管理しやすい。
Supabase 過去指摘の横断検索（Deficiency Database） 複数船・複数検査のデータを SQL で検索・フィルタしたい。 RLS で SELECT のみに制限し、anon キーでも安全に公開できる。 「クラウド DB にデータを置く」体験を今月の範囲で実現。

5. 工夫したポイントと苦戦したポイント

工夫したポイント

  • 4ペイン業務 UI：リスト → 詳細 → 出力の流れを船舶検査の実務に合わせた
  • 意味のある色分け：リスク（高/中/低）、アラート種別、承認状態を Badge で一目で判別
  • 2つのデータソース：Case Review（localStorage）と Database View（Supabase）を1画面で切替
  • 匿名化：公開 URL 用に実船名・実港名をすべて架空名に置換
  • AI との協働：designing-workspace-ui スキルで UI 規律を守りながら開発

苦戦したポイント

  • Vercel デプロイ：output: "export" と Vercel の期待する出力形式の不一致で数回エラー。ログを読んで out/ 生成に戻して解決
  • 静的エクスポートの制約：サーバー側リダイレクトが使えず、vercel.json でルート / → /inspection を設定
  • Supabase RLS：read-only ポリシーの設計と anon キーだけでの安全な公開
  • 今後やりたいこと：localStorage → Supabase への書き込み、ユーザー認証、複数人での共同レビュー

6. 発表の進め方（5分・3点）

  1. どんなデータを保持できるようにしたか
    P4 のフォローアップ文書（6種類のタブ）の編集テキストと承認ステータス。 ブラウザの localStorage に保存し、リロードしても消えない。
  2. どこに保存したか、なぜそこを選んだか
    ユーザーの編集は localStorage（認証なしプロトタイプで最も手軽）。 マスターデータは JSON（静的配信）、過去指摘検索は Supabase（SQL 検索が必要なため）。
  3. 作ってみてどう感じたか
    業務ツールの UI を AI と一緒に作ると、色やレイアウトの「意味」を言語化する大切さが分かった。 Vercel デプロイは設定とログの読み解きが必要で、エラーメッセージを AI に貼ると早く解決できた。
